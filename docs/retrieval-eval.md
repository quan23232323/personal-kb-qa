# 检索策略对比评测：纯向量 / BM25 / 混合 + RRF

> 目的：用**可复核的数据**回答「为什么这个项目要做混合检索」，而不是只在文档里写一句"用了 RRF"。
> 评测脚本随仓库提供：`backend/retrieval_eval.py`。

## 评测设置

| 项 | 设置 |
| --- | --- |
| 语料 | 演示知识库「LLM 学习手册」：21 篇 / **699 个分块**（LLM 教科书 16 章 + 项目文档 4 篇 + 目录说明 1 篇） |
| 向量模型 | `BAAI/bge-small-zh-v1.5`（fastembed / ONNX，512 维，L2 归一化，cosine 度量） |
| 关键词路 | BM25Okapi + **中文字符 bigram 分词**（不引入分词库） |
| 融合方式 | RRF（Reciprocal Rank Fusion，k=60） |
| 取数深度 | 单路取 top10，融合后取 top10，按**文档粒度**去重后判定命中 |
| 评测集 | 25 条中文问题，按文档主题逐篇一条；问题**刻意改写**以避开文档标题用词（否则会高估关键词路）。正解 = 该问题对应文档名 |
| 指标 | R@1 / R@3 / R@5（正解是否出现在前 k 篇）与 MRR（首个命中的排名倒数） |

## 结果

| 策略 | R@1 | R@3 | R@5 | MRR |
| --- | --- | --- | --- | --- |
| 纯向量（语义） | 52.0% | 68.0% | **92.0%** | 0.656 |
| 纯 BM25（关键词） | 48.0% | 72.0% | 88.0% | 0.620 |
| **混合 + RRF 融合** | **68.0%** | **80.0%** | 84.0% | **0.753** |

## 结论

**1. RRF 融合显著提升首位命中。**
R@1 从单路最好的 52% 提升到 **68%（+16pp）**，MRR 从 0.656 提升到 **0.753（+15%）**。
两路召回确实互补：语义路对「换句话问」更稳，关键词路对术语与编号更准——
融合后把各自的强项叠加了。

典型例子：「大模型的输出为什么每次都不一样」
语义路把 `03-Prompt工程.md` 排在第 1（被"输出/不一样"的语义带偏），关键词路正确命中
`01-基础概念.md`，融合后正解回到第 1 位。

**2. RRF 的代价在长尾：R@5 由 92% 降到 84%。**
RRF 按两路排名的倒数相加，会把「只有一路强命中」的候选挤出前 5。
对本项目不构成问题：下游还有**相似度阈值 + 关键词分下限**二次过滤，
且只要进入 top5 就能作为参考资料交给模型；首位命中的提升对"引用来源是否可信"更关键。

**3. 单路做不到的，融合做到了。**
25 条中有多条出现「语义路落在相邻章节、关键词路落在项目文档，融合后回到正解」的情况，
说明两路并非冗余关系。

## 已知局限（如实说明）

- 评测集由我按文档主题构造，**单一标注者、规模 25 条**，不是公开基准；
  结论适用于「验证混合检索的方向性收益」，不宜外推为绝对精度。
- 25 条中 24 条至少有一路在前 5 命中正解。唯一三路全错的是
  「这个项目用了哪些手段避免模型乱编答案」（标注 `项目-DESIGN.md`）——
  该主题实际分散在 `06-评估与安全.md` 与 `04-RAG实战.md`，
  **更可能是标注过窄而非检索失败**。此处保留原样，以维持结果可复核。
- 语料规模偏小（699 分块）。BM25 是**绝对分**且随语料规模增长，
  因此 `bm25_min_score` 这类绝对阈值必须按语料重新标定——
  本项目在 699 分块规模下实测标定为 8.0（无关问题最高约 7.9，相关问题 12~22）。
- 本评测只衡量**检索**（把正确文档召回并把引用给对），不衡量生成质量。

## 复现

```bash
cd backend
PKB_CONFIG=config.demo.yaml .venv/Scripts/python.exe retrieval_eval.py
```

脚本会打印汇总表与逐条明细，并自动列出「三路前 5 均未命中」的问题以便人工复核标注。
